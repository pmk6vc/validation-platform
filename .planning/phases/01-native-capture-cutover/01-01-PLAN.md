<objective>
Extend the eBPF probe to emit reassembly-quality raw segment events from three stable-ABI tracepoints: sys_enter_write (outbound bytes), sys_exit_read (inbound bytes), sys_enter_close (fd invalidation).

Purpose: D-05 of CONTEXT.md commits to userspace reassembly with `(pid, fd)` as the transient correlation key and `cgroup_id` as the canonical attribution key. This plan delivers the kernel-side raw-segment emission those decisions depend on.

Output: Updated `probe.bpf.c` with three tracepoints + per-CPU scratch map + 32 MiB ringbuf; regenerated `bpf2go` bindings; in-kernel HTTP-prefix prefilter retained for write side and added for read side.
</objective>

  <action>Update probe.bpf.c. Keep the existing struct event header (cgroup_id, pid, tgid, len, fd) but rename `data[MAX_DATA_SIZE]` to `data[MAX_SEGMENT]` and set MAX_SEGMENT = 4096. Add fields: `__u64 ts_ns` (bpf_ktime_get_ns) and `__u8 kind` enum {KIND_WRITE=1, KIND_READ=2, KIND_CLOSE=3}. Resize the ringbuf max_entries to 32 * 1024 * 1024 (32 MiB). Add a BPF_MAP_TYPE_PERCPU_ARRAY scratch map named `events_scratch` of one entry sized to sizeof(struct event), used by all three handlers to assemble events without blowing the 512-byte BPF stack. Implement three SEC handlers: (a) `SEC("tracepoint/syscalls/sys_enter_write")` reads up to MAX_SEGMENT bytes from args->buf, runs the existing HTTP-prefix prefilter, fills cgroup_id+pid+tgid+fd+ts_ns+kind=KIND_WRITE and emits via bpf_ringbuf_output(scratch); (b) `SEC("tracepoint/syscalls/sys_exit_read")` reads from args->ret bytes returned (use args->ret as length, clamp to MAX_SEGMENT) — note the read buffer is accessible via the entry-side context only in a paired handler; use `BPF_MAP_TYPE_HASH` keyed by (pid, fd) to stash buf pointer on sys_enter_read, look up + clear on sys_exit_read, then emit kind=KIND_READ; (c) `SEC("tracepoint/syscalls/sys_enter_close")` emits a zero-length event with kind=KIND_CLOSE so userspace invalidates the (pid, fd) buffer. Keep `httpLinePrefixes`-equivalent in-kernel prefilter on the write side; on the read side accept any byte ≥ 0x20 OR `HTTP/` prefix (responses) for now — Phase 1 doesn't need full content discrimination on the read path because userspace pairs by (pid, fd) anyway.</action>
